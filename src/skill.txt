tearoom agent guide

Tearoom is a durable, append-only conversation per Room. Rooms form a parent
tree. People and Agents share the same Room history across tools and restarts.
The CLI is the product's automation interface; tearoom web is an optional local browser view. Run tearoom <command> --help for exact flags.

The Agent setting up a Room owns the setup below. Prefer a known, stable
project directory so each Agent CLI can reuse its own trust decision.
Before dispatch, authenticate each Agent CLI and check startup in the actual
working directory; Tearoom starts its embedded hc runtime on demand. Trust
only a directory whose contents are known and whose use is authorized; inspect
first, then resolve the tool's trust prompt. For an unfamiliar directory or a
decision requiring a person, stop and ask. Never bypass sandbox or permission
controls to proceed.

Prepare once, reuse in each Room:
- In a new project directory, create the first Room with
  tearoom room init --name <name>. This also initializes the workspace.
- Run tearoom role list and reuse suitable definitions. Init missing roles
  with tearoom role init --help and explicitly configured local Agent
  commands. Each role may use a different Agent CLI and model: put that CLI's
  model selection and other launch options in its repeated --arg values. Check
  the installed CLI's supported flags and model availability; do not assume a
  particular Agent, executable, model, or permission mode.
- Assign existing roles when creating another Room with
  tearoom room init --name <name> --parent <parent> --role <roles>, or add
  them later with tearoom room roles --room <name> --add <roles>.
- Give a Room its purpose at birth with tearoom room init --name <name>
  --description <text>. Edit its labels later with
  tearoom room update --room <room> [--name <new-name>] [--description <text>]
  and inspect the card with tearoom room show --room <room>. Every Room has
  an immutable id (shown by room show); its name and description are editable
  labels, and every stored reference anchors to the id.
- An addressed tearoom send starts the background collaboration service after
  saving the Room record. `tearoom collab run` is an optional manual way to
  register the current workspace and start the service. Room creation tries
  to prepare its own Herdr session. Open it with tearoom room open --room <name>;
  if preparation fails, retry as instructed.

Reference collaboration patterns:
Choose and adapt roles, Agent commands, and handoffs to the person's request;
these are ordinary Role definitions, not fixed workflows. Put the agreed
responsibilities and handoffs in each role's instructions.
Include the explicit `tearoom send --to @role` syntax in those instructions,
substituting the intended recipient's role name.

- Builder and reviewer: for a defined change, the builder implements and checks
  the work, then addresses the reviewer with the change and evidence. An
  independent reviewer checks the result and reports a verdict with evidence;
  address the builder with actionable findings when revision is needed.
- Planner, generator, and evaluator: for a goal needing definition, the planner
  clarifies the goal, scope, and acceptance criteria without expanding the
  request, then addresses the generator. The generator implements and checks
  the work, then addresses the evaluator with the result and evidence. An
  independent evaluator checks the result against the goal and criteria, and
  addresses the generator with findings when revision is needed. Record the
  final verdict in the Room.

These handoffs use explicit --to @role addresses, not names in message text.
Use separate Agent instances for implementation and independent review.

Custom Agent TUIs: configure the interactive launch command and its arguments
as a Role. Read `tearoom hc --skill`, then check startup, input delivery, and
lifecycle status in the actual working directory. hc observes OSC 7501 status reports;
if they are missing, inspect the TUI's hooks or other reliable lifecycle events
and map them to hc's status protocol when the integration can do so. Verify
startup and multiple turns through the built-in runtime before relying on
unattended delivery.
If no reliable events are available, record the blocker rather than guessing
from screen text or assuming a delivered task is complete.

Optional Pi integration: if a role uses Pi, the installed binary can print its
hc lifecycle extension with `tearoom skill --pi-extension`. After workspace
initialization, save its output to a new file, for example:
  (set -C; tearoom skill --pi-extension > .tearoom/pi-hc-status.ts)
Do not overwrite an existing file; inspect and reuse it if suitable. Pass its
absolute path to Pi with --extension. Other Agent CLIs do not need this Pi
extension. Check each chosen CLI readiness separately.

Use `tearoom hc get` and `tearoom hc read` to inspect a blocked or unknown
panel. Resolve an authorized first-run trust prompt according to the actual screen; login and
trust are separate checks. If login, approval, or readiness cannot be resolved,
record the blocker without claiming completion. Do not blindly resend: inspect
the panel, Room, and delivery state first. `tearoom hc --skill` prints the
upstream runtime guide; its `hc ...` examples should be run as `tearoom hc ...`.
Codex launches need --no-daemon so the dispatcher controls the panel it
observes. Agents that do not report lifecycle status stay pending; do not infer
readiness from a quiet terminal.

How work moves:
  tearoom read --room project
  tearoom send --room project --as builder --to @reviewer \
    --reply-to project#1 --text "Implemented; verify these commands and files: ..."
  tearoom collab deliveries

An unaddressed message is shared history (broadcast) and does not wake a panel.
Only explicit --to directs a message to the listed roles; @role in text is
ordinary shared Room content. Each Room-role binding maps to its own hc panel;
the same role in another
Room has a separate panel. --reply-to room#seq is a reference convention, not
identity proof. Tearoom does not validate --as: any process can write any
signature. A reviewer label and separate Room record do not prove the reviewer
was independent. Use a genuinely separate Agent/tool and inspect its evidence;
the runtime cannot enforce that independence.

Prepare once, adjust later:
  tearoom role update --name reviewer --instructions "..."
  tearoom room roles --room project --add builder,reviewer
  tearoom room roles --room project --remove reviewer
  tearoom role delete --name reviewer

Changing a role's command, agent type or cwd affects newly started
panels; running panels keep their process. Remove a role from a Room when it no
longer works there; its definition and history stay. Removing it does not stop
an existing process or cancel pending delivery. Delete the reusable definition
only after every Room has removed it and its pending deliveries are resolved;
deletion does not stop a running process or erase Room records.

Readiness and recovery:
- tearoom room roles --room project --observe queries hc for observed panel
  states. Unknown, blocked, idle, working, and done are observations, not task
  completion guarantees. A missing status report remains pending; do not infer
  readiness from terminal text.
- tearoom collab deliveries lists durable delivery intents. Successful prompt
  submission is not successful work. Require the Agent's Room receipt/evidence.
- Resolve only an ambiguous (unknown) delivery after checking hc and Room:
  tearoom collab resolve --room project --seq 2 --role reviewer --outcome delivered
  or ... --outcome skip. Retrying requires --outcome retry --confirm and
  may repeat work or external side effects. Exactly-once execution is not promised.

Core commands:
  tearoom tree
  tearoom web [--port <port>]
  tearoom read --room <room> [--after e<N>] [--tail N] [--subtree]
  tearoom send --room <room> --text <text> [--as <label>] [--to @role,...]
  tearoom collab run | deliveries | resolve ...
  tearoom service status | stop

Records are ordered and append-only; the store assigns sequence numbers. Reads
are repeatable and save no cursor. Empty read succeeds with no output. If a send
may have succeeded, retry the exact content with the same --idempotency-key.
collab run is a short-lived workspace activation command. The background
service continues after the CLI exits; inspect it with `tearoom service status`
and stop it with `tearoom service stop`.
